Harness engineering

Making an AI coding agent produce the architectural standard — not whatever it infers from a prompt.

S2B national e-procurement rebuild · Architect team · presented May 2026

Why

An architect's standard only holds while a person is checking it

On an SI program the architect's remit is clear enough: design the structure, define the standard, control quality in review, and get partner companies onboarded onto the same rules. The problem is that all four depend on people holding the line, and the same failures recur on every engagement.

Uneven skill levels

Senior, junior and outsourced developers read one standard and produce different code.

Standards rebuilt every time

Each new program redefines architecture, rules and templates from scratch, consuming architect time on work already done.

Multi-vendor divergence

Each participating company brings its own style and interpretation. The bill arrives at integration, as rework.

Documented ≠ enforced

A written standard still ends up validated by a senior reviewer in a pull request — a bottleneck, and an inconsistent one.

AI made this worse before it made it better. An agent loses its memory between sessions, so the same request yields different code each time. Output tracks whoever wrote the prompt. And a rule the agent never reads is not a rule — you are back to a person checking every result.

What it is

Constraining the agent, not coaching it

Harness engineering: making the AI act only within rules and scenarios a person defined in advance, instead of judging for itself.

The unit of work is not a prompt. It is a harness — a structure that sits between the developer and the agent and decides what the agent is allowed to load, in what order, and what shape the output must take. Prompts vary; the harness does not. That is the whole point: the same request produces the same result regardless of who asked, how well they phrased it, or which model answered.

Structure

Four layers, with explicit load boundaries

The framework is implemented as a .claude/ directory in every service. Each layer has a defined moment at which it is allowed to enter the context window — which is what keeps the agent accurate and the token cost sane.

LayerLoadedResponsibility
Entry point
CLAUDE.md		Always residentDetects what kind of input arrived — a table name, an HTML file, a spec document, plain language, a persona name — and routes it.
SkillsAlways residentStructure, naming, forbidden patterns, common-module usage. Kept under 150 lines each so residency stays cheap.
CommandsOn call46 predefined scenarios, each a step-by-step workflow. Collect conditions first, start building only once endpoint, parameters and logic are known.
ReferenceSelectivelyVerified example code, split per scenario. A simple query never pulls this in at all.
AgentsPer roleAPI, BFF, UI, review, test, report — isolated contexts, runnable in parallel.

Whatever changes — the coding agent, the developer's seniority, how the request is phrased, the business domain, a fresh session with no memory — the output does not: an API arrives as interfaces / application / domain / infrastructure with CQRS, DTOs and validation rules; a screen arrives as the standard seven-section JS structure with the prescribed common modules.

How it runs

One table name, six steps, a working API

  1. 01
    Developer types a table name — SC_CODE.
  2. 02
    The entry point recognises the input type against already-resident rules and routes to the CRUD scenario.
  3. 03
    That command loads and queries the database schema.
  4. 04
    Only the reference examples this scenario needs are pulled in.
  5. 05
    Role-isolated agents execute — API developer, then test runner.
  6. 06
    Out comes five CRUD APIs, JUnit tests, and the REST Docs specification.

Five input styles are supported, because developers should not have to learn a new way to ask:

InputOutput
A table name5 CRUD APIs · JUnit tests · REST Docs
An HTML fileStandard seven-section JS · grid, form, popup · API wiring
A spec documentBusiness logic · validation rules · BFF and external integration
Plain languageFour-layer CQRS skeleton · backend module · package structure
A persona nameMatched specialist scenario, executed immediately

Design decisions

Why it holds up

The obvious implementation is a single instruction file. It fails in five specific ways, and each of the layer boundaries above exists to answer one of them.

Single fileFour layers
Load efficiencyEverything, every session — wasted tokensOnly what the task needs
Working contextAll rules at once — the agent gets confusedSeparated by task: API work sees API rules
Reference depthAlways consults everythingSimple queries never reach the reference layer
Use casesImprovised — different answer each time46 scenarios defined in advance
Errors & isolated networksSame mistake recurs; rewritten per toolFailures accumulate as reference; swap the entry point

Conditions before code

Commands interrogate first. Nothing is generated until endpoint, parameters and logic are settled.

Failures become assets

Known issues are recorded permanently, so the same AI mistake does not return next session.

Model independence

Swap only the entry point and the same harness runs on Claude outside the client network and Qwen3 inside the air-gapped one.

Portable by copy

Copy one folder, rename domain and packages, and the harness works on a new engagement.

Extensible without regression

A new scenario means adding its own skill, command and reference files — existing scenarios are untouched.

Roles run isolated

Separate agents per role protect each other's context and can run in parallel.

Proof

A number that survives being challenged

Claiming a productivity gain is easy and worth nothing. I built the measurement system to be attacked, and designed each part around a specific objection.

ObjectionDesign answer
"You set a baseline that flattered you."The baseline is the PM-approved WBS — 1,032 items, 3,450 planned man-days. Not an estimate of mine.
"Developers self-reported this."No self-reporting. Effort is collected from tool hooks, with idle gaps over 15 minutes excluded and a 30% overhead factor added back for work outside the session.
"You counted work that already existed."Every artifact is attributed to the commit that introduced it, verified through git history. 466 pre-existing artifacts were excluded automatically.
"That percentage is not credible."Per-item savings are capped at 80% before reporting. The raw values are retained but not claimed.
"This measures your team, individually."Developer identifiers are anonymized at collection. The system reports on the framework, not on people.

79.7% effort reduction — 82 planned man-days delivered in 16.7, across 22 verified deliverables measured so far.

The scope is stated deliberately: 82 of the program's 3,450 planned man-days have been measured to date. Presenting a partial, verifiable number is worth more than a total, arguable one.

Outcome

From documentation to system control

The framework received a company-wide AI Innovation Award and was presented at the Shinsegae Group IT innovation forum and to the CEO as a candidate group-wide standard. What made it worth presenting was not the automation but the shift underneath it.

The architect used to write the standard, argue for it, and verify it in every pull request. Now the system enforces it, and the architect designs the system.

The practical consequences: standards became a transferable asset rather than a per-project rediscovery; senior reviewers stopped being the enforcement mechanism; and the same harness keeps working when the model, the network, or the people change.

AI가 프롬프트를 보고 알아서 판단하는 게 아니라, 정해진 아키텍처 표준대로만 만들게 하는 일.

S2B 전자조달 재구축 · 아키텍트팀 · 2026.05 발표

배경

아키텍트의 표준은 사람이 지켜보는 동안만 유효합니다

SI 사업에서 AA의 역할은 분명합니다. 시스템 구조를 설계하고, 개발 표준을 정의하고, 릴리즈 전에 품질을 통제하고, 협력사에 같은 표준을 전파합니다. 문제는 네 가지 모두 사람이 매번 보장하는 방식이라는 것이고, 그래서 사업마다 같은 문제가 반복됩니다.

개발 인력 수준 편차

시니어·신입·외주가 같은 표준을 다르게 해석해 코드 품질 차이가 상존합니다.

사업별 표준 재수립

신규 사업마다 아키텍처·규칙·템플릿을 처음부터 정의합니다. 이미 한 일에 AA 인력이 반복 투입됩니다.

협력사 결과물 편차

참여 회사마다 스타일과 해석이 다릅니다. 청구서는 통합 단계에서 재작업으로 돌아옵니다.

문서화된 표준의 한계

문서로 정의해도 결국 시니어의 PR 검증에 의존합니다. 병목이 되고, 일관성도 보장되지 않습니다.

AI는 이 문제를 먼저 키웠습니다. 매 세션 기억을 잃기 때문에 같은 요청에도 매번 다른 결과가 나오고, 결과는 프롬프트를 쓴 사람의 실력을 따라갑니다. 그리고 AI가 읽지 않는 규칙은 규칙이 아닙니다. 다시 사람이 매번 확인하는 자리로 돌아옵니다.

정의

AI를 가르치는 게 아니라 묶는 것

하네스 엔지니어링 — AI가 자기 마음대로 판단하지 않고, 사람이 미리 정해둔 규칙과 시나리오대로만 동작하도록 만드는 기술.

작업의 단위는 프롬프트가 아닙니다. 개발자와 AI 사이에 놓여서, AI가 무엇을 어떤 순서로 읽을 수 있고 결과물이 어떤 모양이어야 하는지를 결정하는 구조입니다. 프롬프트는 사람마다 다르지만 하네스는 다르지 않습니다. 그게 핵심입니다. 누가 요청해도, 어떻게 표현해도, 어떤 모델이 답해도 같은 결과가 나옵니다.

구조

로드 경계를 명확히 나눈 4계층

각 서비스의 .claude/ 디렉토리로 구현했습니다. 계층마다 컨텍스트에 들어올 수 있는 시점이 정해져 있고, 이 경계가 AI의 정확도와 토큰 비용을 동시에 지켜줍니다.

계층로드 시점역할
진입점
CLAUDE.md		항상 상주입력 유형을 자동 감지해 분기합니다. 테이블명·HTML·스펙 문서·자연어·페르소나 이름.
Skills항상 상주구조·명명 규칙·금지 패턴·공통 모듈 사용법. 상주 비용을 낮추기 위해 각 150줄 이내로 유지합니다.
Commands호출 시46개 시나리오. 각각 Step-by-Step 워크플로우이며, 엔드포인트·파라미터·로직이 모이기 전까지 개발에 착수하지 않습니다.
Reference선택적검증된 예시 코드를 시나리오별로 분리해 둡니다. 단순 질의는 여기까지 오지 않습니다.
Agents역할별API·BFF·UI·리뷰·테스트·리포트. 컨텍스트를 격리해 병렬 실행합니다.

무엇이 바뀌어도 — Code Agent가 교체되어도, 시니어에서 신입으로 바뀌어도, 호출 방식이 달라져도, 도메인이 추가되어도, 새 세션으로 기억이 초기화되어도 — 결과물은 같습니다. API는 interfaces / application / domain / infrastructure에 CQRS·DTO·검증 규칙까지, 화면은 7섹션 표준 JS 구조에 정해진 공통 모듈 사용법까지.

작동

테이블명 하나, 6단계, 동작하는 API

  1. 01
    개발자가 테이블명을 입력합니다 — SC_CODE.
  2. 02
    진입점이 이미 로드된 규칙으로 입력 유형을 판별하고 CRUD 시나리오로 분기합니다.
  3. 03
    해당 Command가 로드되어 DB 스키마를 조회합니다.
  4. 04
    이 시나리오에 필요한 Reference 예시만 선택적으로 로드합니다.
  5. 05
    역할별로 격리된 Agent가 실행됩니다 — api-developer, 이어서 test-runner.
  6. 06
    CRUD API 5개, JUnit 테스트, REST Docs 명세가 산출됩니다.

설계 결정

왜 이 구조가 버티는가

가장 쉬운 구현은 지시사항을 파일 하나에 몰아넣는 것입니다. 그 방식은 다섯 가지 지점에서 무너지고, 위의 계층 경계는 각각 그중 하나에 대한 답입니다.

단일 파일4계층 분리
로드 효율매 세션 전체 로드 → 토큰 낭비필요한 항목만 선택 로드
작업 컨텍스트모든 규칙이 한 컨텍스트 → AI 혼동작업별 분리 — API 작업엔 API 규칙
참조 깊이항상 모든 정보 참조단순 질의는 Reference까지 오지 않음
유즈케이스즉흥 응답 — 매번 결과 상이46개 시나리오 사전 정의
오류·망분리동일 오류 반복 · 도구별 재작성오류는 누적 자산화 · 진입점만 교체

조건 수집 후 착수

Command가 먼저 질의합니다. 엔드포인트·파라미터·로직이 모이기 전에는 아무것도 생성하지 않습니다.

오류의 자산화

Known Issues를 영구 기록해, 같은 AI 실수가 다음 세션에 재발하지 않습니다.

도구 독립성

진입점만 교체하면 외부망 Claude와 내부망 Qwen3에서 같은 하네스가 동작합니다.

복사로 이식

폴더 하나를 복사하고 도메인·패키지명만 바꾸면 신규 사업에서 작동합니다.

영향 없는 확장

신규 시나리오는 해당 Skill·Command·Reference 파일만 추가합니다. 기존 시나리오는 건드리지 않습니다.

역할별 격리 실행

역할마다 Agent를 분리해 서로의 컨텍스트를 보호하고 병렬로 실행합니다.

증명

공격받아도 남는 숫자

생산성이 올랐다고 주장하는 건 쉽고 아무 가치가 없습니다. 그래서 측정 체계를 공격받는 것을 전제로 만들었고, 각 부분을 특정 반박에 대한 답으로 설계했습니다.

예상 반박설계로 준비한 답
"기준공수를 유리하게 잡았지."기준선은 PM이 승인한 WBS입니다. 1,032건, 계획 3,450MD. 제 추정치가 아닙니다.
"개발자가 자기신고한 거잖아."자기신고가 없습니다. Hook으로 자동 수집하고, 15분 넘는 유휴 구간은 계상하지 않으며, 세션 밖 부대공수는 30% 가산합니다.
"원래 있던 걸 실적에 넣었잖아."모든 산출물을 그것이 처음 도입된 커밋에 귀속시켜 git 이력으로 검증합니다. 기존 산출물 466건은 자동 배제되었습니다.
"그 절감률은 못 믿겠다."건당 80% 상한으로 절사한 뒤 보고합니다. 원값은 보존하되 주장하지 않습니다.
"팀원 개인 평가에 쓰이는 거 아니냐."수집 시점에 식별자를 익명 처리합니다. 이 체계는 프레임워크를 측정하고 사람을 측정하지 않습니다.

공수 79.7% 절감 — 계획 82MD를 16.7MD로. 현재까지 검증된 산출물 22건 기준입니다.

범위를 일부러 밝혀 둡니다. 사업 전체 계획 3,450MD 중 82MD가 지금까지 측정된 분량입니다. 전체를 말하는 논쟁적인 숫자보다, 일부를 말하는 검증 가능한 숫자가 낫습니다.

결과

문서화에서 시스템 통제로

이 프레임워크로 전사 AI 혁신상을 받았고, 신세계그룹 IT 혁신 포럼과 CEO 대상 발표에 그룹 표준 후보로 제안되었습니다. 발표할 가치가 있었던 건 자동화 자체가 아니라 그 아래의 변화였습니다.

예전의 AA는 표준을 쓰고, 설득하고, 매 PR에서 확인했습니다. 이제는 시스템이 표준을 강제하고, AA는 그 시스템을 설계합니다.

실질적인 결과는 세 가지입니다. 표준이 사업마다 다시 발견하는 것에서 이전 가능한 자산이 되었고, 시니어가 더는 강제 수단이 아니게 되었으며, 모델과 망과 사람이 바뀌어도 같은 하네스가 계속 동작합니다.
